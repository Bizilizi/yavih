# Versioning and releasing

## Versions

The package version comes from git tags through setuptools-scm; there is no version string to edit.

| build from | version |
|---|---|
| the tag `vX.Y.Z` | `X.Y.Z` |
| a commit after it | `X.Y.(Z+1).devN+g<commit>` (plus a date suffix when the tree is dirty) |
| a tree without git metadata (not an sdist) | `0.0.0` |

At build or editable-install time setuptools-scm writes `src/yavih/_version.py` (never committed) with the
version, the full source commit and a dirty flag. `yavih.__version__` reads it; `yavih.buildinfo.commit()`
(exposed as `yavih.versions.GIT_HASH`) reports the commit of a checkout (`git rev-parse HEAD`, `+dirty` when
tracked files are modified) or the commit recorded in an installed wheel. Every sidecar, `_meta.json`,
`result.json` and results file records both, so any artefact names the code that wrote it. Neither ever
enters a hash: the package version is provenance, while the [version constants](hashing.md#version-constants)
in `yavih.versions` (feature format, schemas, readout versions) are what decide compatibility.

Bump a version constant in `yavih.versions` when its payload changes, independently of the release
number. Releases follow semantic versioning for the Python API, the CLI and the on-disk formats.

## Continuous integration

`.github/workflows/ci.yml` runs on every push to `main`, every pull request and on demand:

- **ruff** on `src` and `tests`;
- **pytest** on Python 3.10 through 3.14 with CPU torch and ffmpeg, without benchmark data
  (tests that need staged media skip): `pytest tests src/yavih/benchmarks -p no:cacheprovider -o
  addopts="--import-mode=importlib"`;
- **package**: builds the sdist and wheel, runs `twine check --strict`, asserts that the wheel carries no
  maintainer `notes/` and no `.pyc` but does carry `_version.py`, installs it into a clean venv without
  torch, and runs `yavih --version`, `yavih bench lint --all` and `yavih bench files esc50` from an empty
  directory.

`.github/workflows/headers.yml` runs on pull requests that touch `src/yavih/benchmarks/`,
`assets/benchmark-header/` or `src/yavih/headers.py`, and on demand, with read-only permissions: it installs
`.[media]` and `imagequant`, renders every folder's header image with the runner's Chrome
(`python -m yavih.headers --all --contact-sheet headers-contact-sheet.png`), uploads the images and the contact sheet
as the `headers` artifact for review, and fails when a committed `assets/header.src.sha256` is missing or differs
from the current header HTML (render the image and commit it with its sha file).

## Cutting a release

1. Make sure `main` is green and the docs describe the code being released.
2. Tag and push:

   ```bash
   git tag -a vX.Y.Z -m "yavih X.Y.Z"
   git push origin vX.Y.Z
   ```

3. `.github/workflows/release.yml` takes over:
   - **build**: checks out the tag with full history, builds the sdist and wheel, checks that both file
     names carry exactly the tag's version, runs `twine check --strict`, and smoke-tests the wheel without
     torch (`yavih --version` must print the tag's version, `yavih bench lint --all` must pass);
   - **pypi**: publishes to PyPI through trusted publishing (OIDC, environment `pypi`; no API token is
     stored anywhere). An already published version is skipped, so a re-run only refreshes the GitHub
     Release;
   - **github-release**: creates the GitHub Release `yavih X.Y.Z` for the tag with the built files attached
     and notes generated by GitHub from the pull requests merged since the previous tag (categorized by
     label, see `.github/release.yml`). For an existing release it re-uploads the files and leaves the
     notes alone.

To re-run the release for an existing tag: Actions → Release → Run workflow, with `tag = vX.Y.Z`.

Release notes are GitHub's generated notes; there is no changelog file. Label pull requests (`breaking`,
`enhancement`, `bug`, `benchmark`, `documentation`) so they land in the right section (`skip-changelog` leaves one out), and edit the
generated notes on the release page when a change needs more words (for example a new benchmark
protocol version or a feature-format bump users must act on).

## One-time setup

- On PyPI, add a trusted publisher for the project `yavih`: owner `Bizilizi`, repository `yavih`, workflow
  `release.yml`, environment `pypi` (a "pending publisher" before the first upload).
- On GitHub, create the environment `pypi` under Settings → Environments (optionally with required
  reviewers).
- Create the labels used by `.github/release.yml`.
